# 링크 처리 작업 등록 유실 수정

저장 API는 성공했는데 링크가 PENDING에서 영원히 멈추는 문제를 부하 테스트로 발견하고 고친 기록이다.

---

## 한 줄 요약

Redis Stream은 **들어온 작업**을 지키지만, DB 커밋 뒤 Stream에 **넣기까지**는 메모리 안의 `@Async` 작업이었다. 외부 AI 장애로 같은 스레드 풀을 쓰던 색인 작업이 풀을 가득 채우자, Stream 등록 작업까지 거절되어 흔적 없이 사라졌다. 등록 전용 스레드 풀과 PENDING 링크 재발행 배치로 막았다.

## 2. 원인

### 흐름

```
[요청 스레드]
1. 빈 링크(PENDING) 저장 → 커밋
2. 커밋 후 이벤트 리스너 3개를 같은 @Async 풀(taskExecutor: 최대 10, 대기열 100)에 맡김
   ├ 추천 색인 (RecommendationIndexingEventListener) → OpenAI 임베딩
   ├ 챗봇 색인 (ChatbotIndexingEventListener)       → OpenAI 임베딩
   └ Stream 등록 (LinkEventListener)                 → SADD, SETNX, XADD
3. 201 응답
```

### 무슨 일이 일어났나

1. OpenAI가 응답하지 않자 색인 작업이 Spring AI 재시도로 스레드를 오래 붙잡았다.
2. 저장 1건마다 작업이 3개씩(초당 약 30개) 들어와 스레드 10개와 대기열 100칸이 수 초 안에 찼다.
3. 이후 작업은 `TaskRejectedException`으로 거절됐다(로그 17,292건). Stream 등록 작업 5,760건도 포함.
4. 거절은 커밋 이후 정리 단계(`afterCompletion`)에서 일어나 Spring이 로그만 남기고 넘어갔다. 응답은 이미 201.
5. Stream의 재시도·DLQ·알림은 **Stream에 들어온 작업만** 지키므로, 들어가지 못한 작업은 아무도 알 수 없었다.

### 직접 원인과 근본 원인

| 층위 | 내용 |
|---|---|
| 직접 원인 | Stream 등록 작업이 느린 색인 작업과 같은 스레드 풀을 써서 함께 거절됨 |
| 근본 원인 | DB 커밋과 Stream 등록이 서로 다른 저장소에 쓰는 두 단계(이중 쓰기)인데, 그 사이가 기록도 재시도도 없는 메모리 작업이었음 |

같은 구간에서 "커밋 직후 서버 종료"로도 작업이 사라질 수 있다. 스레드 풀 분리만으로는 이 경우를 막지 못한다.

## 3. 수정

### ① Stream 등록 전용 스레드 풀 (`AsyncConfig.linkStreamPublishExecutor`)

- `LinkEventListener`만 `@Async("linkStreamPublishExecutor")`로 분리. 색인 리스너는 기존 `taskExecutor` 그대로.
- 코어 2, 최대 4, 대기열 500, 거절 정책 `CallerRunsPolicy`.
  - 등록은 Redis 명령 몇 개(수 ms)라, 풀이 가득 차도 요청 스레드가 직접 실행하면 버려지지 않고 응답도 거의 늦어지지 않는다.
  - 대신 실행할 작업이 외부 호출(수 초)이었다면 응답 지연으로 이어졌을 것이다. 등록 작업이 가볍기 때문에 고른 정책이다.

### ② 오래 PENDING인 링크 재발행 (`LinkPendingRepublisher`)

- 1분마다 `PENDING`이고 마지막 수정이 5분 넘게 지난 링크를 링크 ID 순으로 페이지 단위로 끝까지 훑고, 한 번에 최대 100건까지 재발행.
- PENDING 상태는 저장 트랜잭션과 함께 커밋되므로 **아웃박스처럼** 쓴다. 어떤 이유로 등록을 놓쳤든 결국 회수된다.
- 판단 규칙
  - **처리 락이 남아 있으면 건너뜀**: Stream에서 처리 중이거나 재시도 대기 중이다. 재발행하면 락 TTL만 계속 늘어나, 진짜로 멈춘 경우에도 락이 영원히 풀리지 않게 된다.
  - **저장한 사용자가 없으면 FAILED로 닫음**: 그대로 두면 매번 조회 결과 맨 앞을 차지해 다른 링크의 재발행을 막는다.
  - 그 외에는 저장한 사용자 전원을 대상으로 `LinkStreamProducer.publishLinkProcessTask` 호출. 첫 호출이 락을 잡고 발행하고, 나머지는 대기자로 합류한다. 중복 발행은 기존 분산 락이 막는다.
- 설정: `link.stream.republish.*` (`enabled`, `fixed-delay-ms`, `stale-minutes`, `batch-size`)

## 4. 결과 (수정 후, 같은 조건)

### 같은 부하 테스트 재측정

| 지표 | 수정 전 | 수정 후 |
|---|---|---|
| 저장 API 요청 | 5,800건 | 5,800건 |
| 저장 API 에러율 | 0.00% | 0.00% |
| 저장 API 응답시간 | 평균 34.73ms, p95 53.06ms | 평균 34.62ms, p95 50.12ms |
| Stream에 등록된 작업 | 40건 | **5,800건 (전부)** |
| Stream 등록 작업 거절 | 5,760건 | **0건** (등록은 전용 풀의 코어 스레드 2개로 처리, 대기열도 넘치지 않음) |
| 측정 직후 PENDING 링크 | 5,760건 (락·메시지 없음 = 유실) | 5,780건, **전부 처리 락 보유** = Stream에서 재시도 대기 중 |

수정 후의 PENDING은 스크래핑을 막아 둔 탓에 재시도를 기다리는 정상 작업이다. "PENDING 링크 수 = 처리 락 수"이므로 추적되지 않는 링크는 0건이다. 색인 작업은 여전히 거절됐다(챗봇 5,742건, 추천 5,748건). 아래 "남은 한계" 참고.

### 등록 유실 상황 재현 → 재발행 배치 검증

부하 테스트에서는 유실이 생기지 않아 재발행 배치가 동작할 일이 없었다. 그래서 "커밋 직후 서버 종료"처럼 등록이 빠진 상태를 직접 만들었다.

- 위 테스트 직후 상태(재시도 대기 중인 PENDING 5,780건)에 **Stream 메시지도 락도 없는 PENDING 링크 50건**(수정 시각 10분 전)을 DB에 추가
- 결과: 재발행 배치가 다음 실행에서 PENDING 5,830건을 확인하고, 락이 있는 5,780건은 건너뛰고 **유실 50건만 재발행** (50건 모두 락 생성, Stream +50건)

```
오래된 PENDING 링크 점검 - 확인: 5830, 재발행: 50
```

### 검증 중 발견해 고친 배치 버그

첫 구현은 "오래된 순 100건"만 조회했다. 재현 테스트에서 이 100건이 모두 **재시도 대기 중인(락이 있는) 링크**라 건너뛰어졌고, 그 뒤의 유실 링크 50건에는 끝내 도달하지 못했다(재발행 0건). 대량 장애로 재시도 작업이 쌓였을 때가 회수가 가장 필요한 순간인데, 바로 그때 배치가 무력해지는 구조였다.

→ 한 번 실행할 때 링크 ID 순으로 페이지를 넘기며 오래된 PENDING을 끝까지 훑고, **실제로 재발행한 건수**가 batch-size에 이르면 멈추도록 변경. 회귀 테스트 `scansPastInFlightLinks` 추가.

## 5. 남은 한계

- **색인 작업 유실**: 색인 리스너는 여전히 기존 풀을 쓰고, AI 장애 시 거절되면 그 링크의 추천·챗봇 색인이 빠진다. 다음 AI 요약 완료나 공개 여부 변경 때 다시 색인되지만, 그 전까지는 검색되지 않는다. 색인을 "처리 완료" Stream의 컨슈머로 옮기면 해결된다.
- **AI 재시도 설정**: Spring AI 기본 재시도가 스레드를 오래 붙잡는다. `spring.ai.retry.*`로 횟수와 대기를 줄이면 색인 풀 포화 자체가 줄어든다.
- **모니터링 없음**: 오래 PENDING인 건수와 스레드 풀 거절 횟수를 지표로 보고 알림을 받아야 남은 틈이 조용히 넘어가지 않는다.
- **재발행 조회 비용**: 매 실행마다 오래된 PENDING 전체를 훑고 링크마다 Redis 락을 확인한다. 5,830건에서는 문제가 없었지만, PENDING이 수십만 건 쌓이는 규모라면 커서를 실행 간에 이어 가고 `(processing_status, updated_at)` 인덱스를 추가한다.
- **복구 처리 속도**: Stream 복구 작업은 10초마다 20건(`link.stream.recovery.batch-size`)씩 재처리한다. 이번처럼 5,800건이 한꺼번에 실패하면 재시도를 모두 거쳐 끝나기까지 약 3시간이 걸린다. 유실은 아니지만 대량 장애 후 회복이 느리다. 장애 규모에 맞춰 batch-size를 늘리거나 서킷 브레이커로 장애 중 재시도 자체를 줄이는 방법이 있다.
