# 카테고리 추천 캐시 스탬피드 방지

카테고리 추천 후보 캐시(`categoryRecommendationIds`)가 비는 순간 같은 카테고리 요청이 몰리면, 요청 수만큼 벡터 검색(카테고리명 OpenAI 임베딩 + Elasticsearch 검색)이 동시에 실행되던 문제를 같은 키 요청 병합으로 막은 기록이다.

---

## 1. 문제

- #119에서 카테고리 추천 후보 ID를 Redis에 캐싱했다(TTL 30분).
- 이 캐시는 링크 저장·삭제, 공개 여부 변경, AI 요약 완료 때마다 **전체를 비운다**(`allEntries = true`). 즉 캐시가 비는 일이 TTL 만료보다 훨씬 자주 일어난다.
- `@Cacheable`은 캐시 miss인 요청마다 각자 원본을 조회한다. 캐시가 빈 순간 같은 카테고리 요청 N건이 들어오면 벡터 검색도 N번 실행된다(캐시 스탬피드).
- 벡터 검색 1회는 OpenAI 임베딩 API 호출을 포함하므로, 중복 조회는 응답 지연뿐 아니라 **외부 API 비용과 요청 한도(429)** 문제로 이어진다.

### 왜 `@Cacheable(sync = true)`가 아닌가

`sync = true`면 같은 키의 miss를 하나로 묶어 주지만, Spring은 `sync`와 `unless`를 함께 쓰지 못하게 한다. 이 캐시는 #127에서 **빈 결과는 캐싱하지 않도록**(`unless`) 했다. 색인 전에 조회된 빈 결과가 30분 동안 굳는 문제를 막기 위해서다. 그래서 `sync`로 바꾸면 그 보호가 사라진다.

---

## 2. 해결: 같은 키 요청 병합

`RecommendationCacheService.getCategoryRecommendationUserLinkIds`

```
캐시 hit → 바로 반환
캐시 miss →
  진행 중 조회 목록(ConcurrentHashMap<category, CompletableFuture>)에 putIfAbsent
    ├ 내가 처음 → 캐시 재확인 → 벡터 검색 → 결과가 있으면 캐시 저장 → future 완료 → 목록에서 제거
    └ 이미 진행 중 → 그 future를 기다려 같은 결과를 받음
```

- 빈 결과는 여전히 캐싱하지 않는다. 같은 순간 몰린 요청끼리만 결과를 공유한다.
- 첫 요청의 조회가 실패(ES 장애 등)하면 기다리던 요청에도 같은 예외를 전달해, 호출부의 DB fallback이 똑같이 동작한다.
- 병합 목록 등록 직전에 다른 요청이 캐시를 채웠을 수 있어, 처음 요청도 조회 전에 캐시를 한 번 더 확인한다.

---

## 3. 측정

`RecommendationCacheStampedeTest` (실제 Redis 7.2 + 운영과 같은 `RedisConfig`의 `RedisCacheManager`, Spring 캐시 프록시)

- 벡터 검색만 가짜로 대체: 호출 횟수를 세고, 1회당 **300ms 지연을 가정**(임베딩 API + ES 검색)
- 스레드를 `CountDownLatch`로 동시에 출발, 시나리오당 5회 반복, 전체를 3번 실행해 결과가 같은지 확인

```bash
docker run -d --rm --name stampede-redis -p 6391:6379 redis:7.2-alpine
REDIS_TEST_PORT=6391 ./gradlew test --tests '*RecommendationCacheStampedeTest' -i
```

| 시나리오 | 수정 전 | 수정 후 |
|---|---|---|
| 캐시가 빈 카테고리 1개에 동시 100건 (×5회, 요청 500건) | 벡터 검색 **500회** | **5회** (회당 1번) |
| 전체 무효화 직후 카테고리 10개 × 20건 (×5회, 요청 1,000건) | 벡터 검색 **1,000회** | **50회** (카테고리당 1번) |
| 빈 결과 카테고리에 동시 50건, 이어서 1건 | 50회 + 1회 | 1회 + 1회 (빈 결과는 여전히 캐싱 안 함) |

3번 실행 모두 같은 수치가 나왔다.

### 응답 시간은 왜 거의 같은가

| | 수정 전 | 수정 후 |
|---|---|---|
| 동시 100건 응답 | avg 약 313ms, p95 약 317ms | avg 약 310ms, p95 약 313ms |

가짜 벡터 검색은 동시 호출이 늘어도 느려지지 않는다(고정 300ms). 그래서 이 측정에서는 기다리는 요청과 직접 조회하는 요청의 시간이 비슷하다. 실제 ES와 OpenAI는 동시 호출이 몰리면 느려지거나 429로 거절하므로 수정 전 응답은 더 나빠질 수 있지만, 그 정도는 측정하지 않았다. **이 개선의 근거는 응답 시간이 아니라 외부 호출 횟수다.**

## 4. 한계

- **JVM 안에서만 병합한다.** 서버가 N대면 카테고리당 최대 N번 조회한다. 운영은 1대라 충분하고, 늘어나면 Redis `SET NX` 락으로 서버 간 병합을 하거나 만료 전에 미리 갱신하는 방식으로 확장한다.
- **전체 무효화 자체는 그대로다.** 링크 하나가 저장돼도 모든 카테고리 캐시가 빈다. 바뀐 링크가 속하는 카테고리만 비우면 miss 자체가 줄어든다.
- 사용자별 저장 링크 캐시(`userLinkIds`)는 키가 사용자마다 달라 같은 키 동시 요청이 드물어 적용하지 않았다.
